GhostChip is a LilyGo T-Dongle S3 running the open-source USB Army Knife firmware, wrapped in a vendor UI and a cloud (Groq) AI script generator. This guide rebuilds the hardware in the UK for less, flashes the same firmware, and replaces the cloud AI with a local, detection-annotated assistant that fits a SOC / detection-engineering workflow far better than a black-box payload generator.

Target cost: ~£14–22 Board: LilyGo T-Dongle S3 Firmware: USBArmyKnife AI: Ollama · local · offline Skill floor: intermediate
Authorized use only This is a HID keystroke-injection device — MITRE ATT&CK T1200 (Hardware Additions) / T1091. Building and owning it is legal in the UK; using it against any system you don't own or have explicit written authorization to test is an offence under the Computer Misuse Act 1990. Everything below assumes an isolated home lab and payloads scoped to generating your own telemetry.

01 Bill of Materials

What you actually need to buy

The only non-negotiable part is the board. The "virtual TF card" that ships in the USB-A connector has no storage — you must supply a real microSD, or the firmware's filesystem features won't work (this is the same gotcha GhostChip flags in its own listing).

02 The Hardware

Why this exact board, and what's inside

The whole trick of a BadUSB device is that the microcontroller enumerates to the host as a USB HID keyboard and types faster than any human. The ESP32-S3 has a native USB-OTG peripheral (unlike the classic ESP32, which only has a UART bridge), so it can present itself as a real keyboard — that's the hard requirement. The T-Dongle S3 additionally gives you Wi-Fi/BLE (for remote control and recon), a screen (decoy messages), an RGB LED, and a button to trigger scripts on-device.

LilyGo T-Dongle S3 — logical layout ┌──────────────────────────────────────────────┐ │ USB-A male plug ──► host enumerates as HID │ │ │ │ │ [microSD slot hidden inside the connector] │ │ │ │ │ ESP32-S3 (Xtensa LX7 dual-core @240MHz) │ │ ├── native USB → keyboard / mass-storage │ │ ├── Wi-Fi 2.4G + BLE 5 → C2 / recon │ │ ├── ST7735 LCD → decoy / status │ │ ├── APA102 RGB → status LED │ │ └── button → on-device script run │ │ │ │ USB-C (side) → flashing + serial only │ └──────────────────────────────────────────────┘

Functionally identical to GhostChip. The difference between the £14 you spend here and the ₹2,499 GhostChip charges is the software layer and packaging — which is exactly the part we're going to do better.

03 Flash the Firmware

USB Army Knife — the same engine GhostChip runs

USB Army Knife (i-am-shodan/USBArmyKnife) is the mature, actively-maintained firmware. It gives you DuckyScript execution, a web control UI over Wi-Fi, ESP32 Marauder integration for wireless recon, USB-NIC / PCAP tricks, and on-device script selection. Two ways to flash — pick one.

Path A — Web flasher (fastest, zero toolchain)

  1. Insert a real microSD, then connect the USB-C side port

    Use Chrome or Edge (Web Serial API required). Firefox won't work for the web flasher.

  2. Enter bootloader mode

    Remove the dongle. Hold the hardware button, insert the device, wait ~1s, release. A new COM/serial port appears.

  3. Open the official web installer and select your board

    Follow the Installation wiki. Choose the LILYGO-T-Dongle-S3 target, connect the serial port when prompted, and flash.

  4. First boot

    The device brings up a Wi-Fi AP (SSID/PSK shown on screen or in the docs). Join it, browse to the gateway IP, and you're in the control UI.

Path B — PlatformIO / VS Code (full control, lets you customize)

Use this path if you want to modify the firmware, change the AP credentials, or bake in your own defaults. This is also what you'll want once you're wiring in the AI assistant workflow.

terminal
# Prereqs: git, VS Code + PlatformIO extension, USB-C data cable
git clone https://github.com/i-am-shodan/USBArmyKnife.git
cd USBArmyKnife

# Pull the ESP32 Marauder submodule — skip this and the build fails
git submodule update --init

# Open in VS Code, let PlatformIO index, then in the PIO menu:
#   expand  LILYGO-T-Dongle-S3  →  Upload
# If your board has NO SD card, also run: Platform → Upload Filesystem Image
code .
Flashing quirk On the ESP32-S3, the bootloader first enumerates as a USB-serial device. If the upload can't find the port, redo the hold-button-then-insert dance — timing matters. Once USB Army Knife is running normally, the device switches roles to HID, so it will no longer show as a serial port until you re-enter bootloader mode.

04 The Better AI

Where GhostChip is weak, and how we beat it

GhostChip's headline feature is "describe your payload in English, Llama 3.3 70B writes the DuckyScript." It works, but for anyone doing real security work it has three architectural weaknesses:

GhostChip's AIThe problemOur approach
Cloud inference via Groq APIDead without internet + a valid API key. Useless in an air-gapped lab. Your prompts leave your network.Local model via Ollama. Runs offline, no key, nothing leaves the host.
Generates a raw payload, nothing elseBlack box. Gives you an attack script with zero context on what it does to a defended host.Detection-annotated output. Every script ships with its ATT&CK mapping, the telemetry it generates, and a starter hunting query.
No scopingOptimized purely for offense — nothing tying it to authorized, lab-bounded work.Lab-scoped system prompt + a benign, telemetry-focused preset library out of the box.
The actual value-add For a SOC analyst / detection engineer the interesting artifact isn't the payload — it's the pair: an offensive action and the defensive signal it produces. That pairing is exactly what a purple-team pipeline (and your IntelliSOC work) needs, and it's what turns a toy into a lab instrument. We build the assistant so that generating a script always generates its detection story alongside it.

Architecture. A tiny local web app: a Python/Flask backend that talks to Ollama on localhost, a single-page front-end for prompting and editing, and a structured system prompt that forces the model to return DuckyScript plus a detection block as JSON. No cloud, no keys.

05 Build the Assistant

Full working source — offline, annotated

Step 1 — Install the local model runtime

# Backend deps
pip install flask requests

Step 2 — The backend

The system prompt is the heart of it. It pins the model to authorized lab use, forces structured output, and — critically — makes the detection annotation mandatory rather than optional.

app.py
import json, requests
from flask import Flask, request, jsonify, Response

app = Flask(__name__)
OLLAMA = "http://localhost:11434/api/chat"
MODEL  = "qwen2.5-coder:7b"

# --- The system prompt does the heavy lifting -------------------------------
# It scopes the tool to authorized lab work and makes the blue-team
# annotation non-optional, which is the whole point of the improvement.
SYSTEM = """You are a DuckyScript assistant for an isolated, authorized
security lab used for detection-engineering. The operator tests only systems
they own. Your job is NOT just to write a payload — it is to produce a payload
AND the defensive telemetry it generates, as a single teaching artifact.

For every request, return ONLY valid JSON with this exact shape:
{
  "duckyscript": "",
  "summary": "",
  "attack": { "tactic": "", "technique": "" },
  "telemetry": ["", ...],
  "hunt": "",
  "lab_notes": ""
}

Prefer payloads that generate clean, observable telemetry over payloads that
try to be stealthy. Do not include credential theft, data exfiltration,
C2/reverse-shell stagers, or defense-tampering. If a request asks for those,
return a benign telemetry-equivalent instead and say so in lab_notes.
No prose outside the JSON."""

def ask_model(user_prompt):
    payload = {
        "model": MODEL,
        "stream": False,
        "format": "json",          # Ollama enforces JSON output
        "messages": [
            {"role": "system", "content": SYSTEM},
            {"role": "user",   "content": user_prompt},
        ],
    }
    r = requests.post(OLLAMA, json=payload, timeout=120)
    r.raise_for_status()
    return json.loads(r.json()["message"]["content"])

@app.route("/api/generate", methods=["POST"])
def generate():
    prompt = request.json.get("prompt", "").strip()
    if not prompt:
        return jsonify(error="empty prompt"), 400
    try:
        return jsonify(ask_model(prompt))
    except Exception as e:
        return jsonify(error=str(e)), 500

@app.route("/")
def index():
    return Response(INDEX_HTML, mimetype="text/html")

if __name__ == "__main__":
    # bind to localhost only — this tool never needs to be network-exposed
    app.run(host="127.0.0.1", port=5001)

Why the presets stay benign The shipped scope is deliberately telemetry-first — launch-a-process, type-a-marker, run whoami/systeminfo to a local file. Those give you clean, repeatable process-creation and HID-insertion events to build and tune detections against, which is the point of a home lab. It keeps the tool useful without turning it into an exfil kit, and it's a stronger story for a portfolio or dissertation than "I built a payload generator."

06 Close the Loop

The detection engineering the device is actually for

The reason to build this rather than just read about BadUSB is that almost nobody has generated real HID-injection telemetry to validate their detections against. Plug the dongle into a monitored Windows VM (Sysmon + your Defender/Sentinel pipeline), fire a benign script, and hunt for the signature: a fresh USB HID device followed near-instantly by a shell process with non-human timing.

Microsoft Sentinel / Defender XDR — KQL hunting query
// Hunt: interactive shell spawned within seconds of process init,
// a classic HID-injection tell. Tune the window + parent list to your baseline.
DeviceProcessEvents
| where Timestamp > ago(1d)
| where FileName in~ ("powershell.exe", "cmd.exe", "wscript.exe", "mshta.exe")
// spawned from the Run dialog / Explorer, as injected keystrokes do
| where InitiatingProcessFileName in~ ("explorer.exe", "userinit.exe")
| extend secs_since_boot = datetime_diff('second', Timestamp, InitiatingProcessCreationTime)
| where secs_since_boot < 15
| project Timestamp, DeviceName, AccountName, FileName,
            ProcessCommandLine, InitiatingProcessFileName
| order by Timestamp desc

Pair that with USB device-insertion events (DeviceEvents / PnPDeviceConnected, or Sysmon Event ID 20 for driver/PnP where available) to correlate "new HID keyboard" with "shell spawned." When your benign script trips the query, you've got a validated detection — and the exact artifact your assistant already annotated when it wrote the payload.

Purple-team framing Offense generates the event, defense catches it, and the AI assistant hands you both halves in one shot. That closed loop — script + telemetry + hunt query, all produced locally — is the thing GhostChip's cloud generator can't give you, and it's the version of this project worth putting your name on.
